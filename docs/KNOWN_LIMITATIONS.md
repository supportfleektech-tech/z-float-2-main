## Functional limitations

1. **[OPEN — Batch D] Sandbox rails only — adapters contract-tested, not certified.** All payment execution goes through the `local-sandbox` mock provider. The Daraja (M-Pesa) adapter is verified 10/10 against a local emulator speaking the real wire protocol (OAuth, B2C, STK, status, reversal), but no real M-Pesa/bank/PSP call has been made and no real money moves. Going live requires Safaricom credentials + their certification (test shortcode/passkey, allow-listed callback URLs), then PesaLink/RTGS/EFT adapters.
2. **CUSTOM cron parsing is real but falls back on bad expressions.** `nextRunFor` (payments-core) evaluates cron expressions with cron-parser; unparseable expressions (and CUSTOM with no expression) fall back to +7 days to prevent schedule storms (a no-expression fallback returning the same date would re-fire on every dispatch run).
3. **Airtime products are catalog-only.** Airtime purchases create valid payments through the sandbox; the real airtime provider integration (Safaricom/Airtel/Telkom APIs) is not implemented.
4. **CSV export exists; XLSX/PDF do not.** `reports.generate` writes tenant-scoped transaction/fee CSVs to `REPORT_STORAGE_DIR` (shared dir, default `data/reports`); download via `/api/reports/{id}/export`. XLSX and scheduled e-mailed reports are future work.
5. **File scanning defaults to `mock` driver.** The `clamav` driver is implemented (clamd TCP protocol) but not exercised against a live ClamAV daemon; tune `MALWARE_SCANNER_DRIVER`/`CLAMAV_HOST`/`CLAMAV_PORT` before production.
6. **Email/SMS providers are contract-tested against local mocks, not live.** The worker delivers EMAIL (`sink|smtp|console`) and SMS (`http` — Africa's Talking-compatible wire, `|console`) through configured drivers; the demo runs EMAIL→sink files in `data/mailbox` and SMS→a local AT-compatible gateway mock (artifacts in its JSON-line log). Wire behaviour is unit-tested (6/6); live sending needs real credentials (SMTP/SES; AT/Twilio) plus allow-listed sender IDs.
7. **Invitation emails are not sent.** The invite token is returned in the API response for demo convenience; production must email it and never expose it in responses.
8. **Bank webhook endpoint relies on `bank-psp` registry key.** The generic `/api/webhooks/bank` route resolves provider `bank-psp` from the registry — confirmed present (`packages/providers/src/index.ts`) and verified live in the demo (header `x-webhook-signature` + `BANK_API_SECRET`; dev value `mock-bank-dev-secret` in `.env`). In production, set a real shared secret and never ship the dev value.

## Data & correctness notes

9. **Ledger health runs periodically, not on every payment.** Journals are written on funding/execution/reversal; the worker's `ledger.health` housekeeping (startup + every 10 min) re-checks double-entry invariants per tenant and flags `ledger.health.imbalance` audit events. It is not a per-payment pre-validation.
10. **Concurrent wallet funding is serialized by row lock** (SELECT ... FOR UPDATE) — correct by design (atomic increments), a hotspot only under extreme volume. (C-3) resolved the audit half: every funding/reserve/release/apply and every denied double-spend attempt now lands in the immutable per-wallet reservation ledger (`wallet_ledger_entries`), which also makes the serialization fully auditable/replayable.
11. **Reconciliation import is CSV/manual.** Statement-import reconciliation (CSV `provider_reference,amount,date`) matches by provider reference + amount and flags AMOUNT_MISMATCH/UNMATCHED exceptions; there is no automated provider pull (Daraja API) yet (Phase 10 SEAM). Resolve/reopen/comment is an in-app, audited workflow since GAP Phase 3 (portal + cross-tenant admin view; every action in `recon_exception_activity` + the audit log) — CSV is no longer the only way to act.

## Security & compliance posture

12. **Demo credentials shipped in seed.** `demo@zfloat.app / Demo@12345` and `admin@zfloat.app / Demo@12345` exist only when `SEED_DEMO_DATA` is on. Production must run with demo seeding disabled and no shared credentials.
12b. **Session cookie `Secure` is opt-in** via `COOKIE_SECURE=true` (not auto-forced by NODE_ENV) so the demo works over plain http previews. Real deployments MUST set `COOKIE_SECURE=true` (see production-checklist).
13. **No regulatory claims.** Z-float is not a licensed PSP/bank. All payments are executed by regulated partners; the demo simulates those rails.
14. **Watchlist data is demo-only; no licensed screening feed.** The KYC/AML engine (`@zfloat/kyc`: deterministic token matching with Jaccard scoring, PEP/sanctions/adverse entries, screening rows, case workflow, document intake gated on the malware scan, `submitPayment` gate that risk-flags and forces approval on a hit) runs against `aml_watchlists`, seeded with four fictional demo entries (e.g. "Grace Wambui"). There is no live sanctions-list provider, no real identity verification, and decisions are made by platform admins in the sandbox — a licensed feed + named compliance officers are required before real use.
14b. **Maker-checker scope.** The approvals engine (`@zfloat/approvals`) gates every sensitive execution: payments and batch payouts (amount/risk policy), payee-book additions (a payee registers as PENDING and only an independent approver's sign-off makes it payable), payment reversals (the maker's request never moves funds — a checker's approval executes the provider reversal + compensating journal), invitations into roles that carry approve/reverse/manage powers (the invite is PENDING until a checker approves; registration into the role is refused before that — `ROLE_AWAITING_APPROVAL`), and **platform configuration**: catalog billers/airtime AND pricing/fee rules, approval-policy publish/pause/version edits, and feature-flag toggles — every platform-config create/update/delete is staged via `platform_config` approval requests (HTTP 202 `PENDING_APPROVAL`) and applies only after a SECOND platform admin approves in the config approvals centre `/admin/approvals` (`ops@zfloat.app` is the seeded checker; migration 014; `/api/admin/config-requests`; staged payloads validated per kind with direct-route semantics). Apply happens under the approver's authority with the original audit trail intact: fee-rule changes bump the version and append `fee_versions` snapshots (`pricing.rule.updated`); approval-policy rule edits archive the live rules into `approval_policy_versions` and bump v→v+1 (`approval.policy.update`), pause/activate flip `active` only (`approval.policy.pause|activate`); flag toggles audit `feature_flag.updated`. Apply cores re-read the live row so queued changes never clobber each other, and apply conflicts surface as `applied:false` + `execution_error` with a `platform.config.apply_failed` audit — never a silent failure. The creator can never approve their own request, even via delegation. Deliberate one-person surface: under-threshold single payments (the gate engages by amount/risk, not per payment; demo mode runs a built-in KES 10,000 threshold policy; production enforces the tenant's ACTIVE published policy and **fails closed** — `APPROVAL_POLICY_REQUIRED` — when none is published). Non-goals: feature-flag percentage rollout is not exposed in the console (key-level toggles are), and the approvals centre renders proposed changes as JSON rather than per-field form diffs.
15. ~~**TOTP secrets encrypt at rest** (AES-256-GCM) but the key management is environment-variable based (`ENCRYPTION_KEY`) — production should use a KMS.~~ **(C-2) Resolved**: `@zfloat/secrets` vault — `ENCRYPTION_KEY`/`SESSION_SECRET` and all provider secrets resolve env-first then from AES-256-GCM envelopes wrapped by AWS KMS in production (`SECRETS_DRIVER=kms`); local-driver envelopes for dev/staging; CLI `pnpm secrets set|list|unset`; applied at boot by web (secret-guard), worker and relay; fail-closed on vault errors. Live KMS proof still pending real AWS credentials.

## Operational limitations

16. **`next build` must run with a production-mode environment.** Building with `NODE_ENV=development` in the environment (e.g. sourcing a dev env file) makes Next compile a mix of dev/prod server runtimes and prerender fails for every page (`<Html> should not be imported` / `useContext` null). Use the documented build env (`NODE_ENV=production`, non-zero `ENCRYPTION_KEY`/`SESSION_SECRET`, `SEED_DEMO_DATA=false`, `MALWARE_SCANNER_DRIVER=clamav`; `DEMO_MODE=true` only for the deliberate demo-walkthrough deployment class — see the env guard in `packages/config/src/env.ts`). See runbook RB-10.
16b. **Object storage is driver-abstracted (`local` | `s3`) but only locally verified.** The `@zfloat/storage` package (put/get/head/delete/presign, traversal-safe keys, tenant prefixes) backs KYC evidence uploads and report exports, selected by `STORAGE_DRIVER`. The `s3` driver is contract-tested (8/8) against a real MinIO server speaking the S3 wire protocol and was exercised live through the product (report export `s3://reports/{id}.csv`, KYC upload objects, verified in the MinIO bucket; binaries at `scripts/tools/minio`). No AWS S3/Lifecycle/retention or bucket-policy hardening has been validated — that is prod configuration, not code.
17. **`db:reset` drops the database.** Stop the web app and worker first (their Postgres pools are killed by `DROP DATABASE ... WITH (FORCE)` and they exit). RB-01 documents the safe order.
18. **Integration test suites share one test database** (`DATABASE_URL_TEST`). They are DB-truncating and must run sequentially — `test:unit` / `test:integration` scripts enforce `--workspace-concurrency=1`. Running `pnpm -r test` directly will race.
19. **Single-instance Postgres assumption.** Migrations, triggers and the worker are tested against one DB; multi-region or read-replica setups are untested. (C-1) added the topology rules and constraints in runbook RB-13 — read it before attempting replicas.
20. ~~**Outbox poller runs in-process.** The worker's outbox poller (5s) is fine for demo scale; production should run the poller as its own deployment~~ **(C-1) Resolved**: shared `runOutboxPoller` in `@zfloat/payments-core` runs embedded in the worker AND standalone as `services/outbox-relay` (`pnpm dev:relay`/`start:relay`, Docker target `relay`); Postgres advisory-xact-lock lease arbitration means any number of relays + the worker coexist with exactly-one dispatch per tick (integration 5/5 + live proof). Production should still prefer N relays over the embedded one for isolation.
21. **BullMQ retry policies — explicit per queue (GAP-ANALYSIS Phase 7, resolved).** `QUEUE_POLICIES` + `resolveJobOptions` in `packages/queue` now set attempts/backoff per queue (money/batch/schedule/monitor/outbound/recon 5, webhook.process 8, notifications 10, files/reports 3; exponential 1–5s); unit spec `packages/queue/test/policies.test.ts` 3/3. Per-queue tuning for a production workload remains an ops exercise — the Phase 9 soak profiles showed zero job failures, so no re-tuning was warranted on observations. Exception with an explicit in-engine ladder: `webhooks.deliver` — `deliverWebhook` owns its retries (2s→30s exponential, max 5, recorded on `webhook_deliveries` with `next_retry_at`/`last_error`) and enqueues each attempt with a unique job id, so BullMQ's default attempts never double-drive it. Note: BullMQ custom job IDs must not contain `:` — Z-float uses `pay-{id}` / `wh-{id}` / `batch-{id}` accordingly.
22. **No rate limiting on provider webhook ingestion beyond idempotency.** Signature verification + dedupe exist; consider per-provider IP allowlists at the load balancer.

## Test coverage gaps

23. ~~Playwright E2E runs against the production build (`next start`) with the demo DB seeded; the suite had one rotating flaky member (34 spec-runs → 33 passed + 1 flaky retry-pass between `health-alerts.spec.ts` and `developers.spec.ts`).~~ **(Post-review close-out: eliminated.)** Full suite is now **34/34 green** at `--retries=0` (re-gate evidence `data/e2e/final-suite-*.log`, including a from-scratch rebuild after a full environment recycle: `final-suite-20260904-020234-retries0-freshenv.log`, 34 passed in 1.3m — the gate procedure itself reproduces; targeted determinism evidence: `health-alerts` + `developers` + `system-health` ×3 repeats each with `--retries=0` → 9/9). Three root causes were found and fixed:
    - `health-alerts.spec.ts` raced the /admin/health panel's **30s refresh cadence** (fixed 30s UI wait vs 30s cadence) and targeted leftover rows from earlier runs by shared text — the spec now polls the server-side ops-alert list for the dispatch it just created (SENT) and then asserts the rendered badge after one reload. The first full re-gate also exposed a **real regression from the chaos hardening**: the bounded Redis client (`enableOfflineQueue:false`) was created per request and used immediately, so the first command always raced the socket handshake and health checks, rate limiting (fail-open silently), alert cooldowns and metrics all failed against a *healthy* Redis (`system-health` failed deterministically). Bounded clients are now a per-process **warm singleton** (one per Redis URL), and the callers that used to `quit()` their per-request client no longer do — the fail-fast contract now applies to outages only, with background reconnect (so recovery needs no process restart). A further suite run then caught a second real issue: the worker's `zfloat:ledger:last` health record (written at startup + every 10 min with EX 600) left long windows after a Redis restart where /admin/health reported "no ledger health run recorded yet" and the `ledger_unknown` rule fired WARN emails — the record now uses **EX 900**, interval/startup failures log explicitly, and the ~30s heartbeat **self-heals a flushed record within ~1 min** (a Redis restart wipes the key regardless of TTL; verified live: record restored ~56s after a simulated flush, and the redis-outage drill on this build shows no `ledger_unknown` residue). The stack recipe is unchanged: sandbox runs on `/tmp/zf-build-env.sh` (`NODE_ENV=production`, `DEMO_MODE=true` — an explicit, legitimate deployment class for the demo walkthrough, never auto-seed: `SEED_DEMO_DATA=false`, `MALWARE_SCANNER_DRIVER=clamav`) with `scripts/tools/clamd-stub.mjs` standing in for a real ClamAV daemon on 127.0.0.1:3310 and the queue worker + outbox relay running separately (see runbook RB-10).

## Platform scope (launch decisions)

28. **KES-only launch (documented deferral).** Wallets, payments, fees, reconciliations and
    the provider adapters are single-currency (KES, minor units everywhere). Multi-currency
    is deliberately deferred — it is an architectural change (money types, FX/reservation
    semantics, per-currency provider routing, reporting) and would invalidate the "single
    unit of account" invariants the ledger + reconciliation rely on. The KES-only scope is a
    product decision, not an accident of implementation.
